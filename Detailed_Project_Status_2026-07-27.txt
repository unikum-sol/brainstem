# BrainStem Detailed Project Status

**Status date:** 27 July 2026  
**Python package:** `ki_system`  


## 1. Executive Summary

BrainStem is a self-learning language and text understanding system built around contextual hypotheses, error-driven learning, 
replay and consolidation, and a twelve-system neuromodulator architecture. Its long-term objective is to improve autonomously through observation, 
contextual hypothesis formation, error processing, revision, sleep-like consolidation, and controlled promotion of sufficiently supported hypotheses, 
while ultimately providing measurable value in real user dialogue.

The current repository has completed the Stage-B implementation and readiness work that was planned for the frozen pre-validation state. 
A bundled Stage-B readiness test was executed against the current local project and database. It returned `STAGE_B_READY_FREEZE_PASS` with 
zero failures and zero warnings. This establishes that the current codebase, schema, bootstrap path, safety gates, Stage-B control contracts, 
and included integration tests are mutually consistent for the tested state.

A new full 1,344-cycle stability and drift validation for this exact frozen Stage-B state is currently running. Its result is not yet available 
and must not be reported as passed until all requested cycles complete and the final report confirms the required invariants.

### 3.3 Modern Candidate and Observation Paths

The Modern Gap Candidate Bridge remains:

- checkpoint-based
- bounded to a maximum of 512 hypotheses per cycle
- `observed_only`
- shadow-only
- disconnected from productive `internal_learning_gaps`, Attention, Phase-5f, Phase-5g, Phase-5i, Facts, Relations, and Questions writes

The Stage-B E/F integration test confirmed both meaningful states of the gap-flow contract:

- real candidates can be recognized as `real_candidates_observed_shadow_only`
- an empty source interval is represented as `measured_zero_no_new_sources`, rather than being treated automatically as an error

### 3.4 Computational Kernels and Guarded Adapters

Pure computational kernels and guarded adapters are present for the consolidated neuromodulator calculations. The guarded architecture 
preserves wrapper-owned behavior and keeps the canonical production path protected while shadow evidence is collected.

The current safety position remains conservative:

- no unvalidated runtime cutover
- no productive gate opened by the adapter work
- no replacement of evidence, transaction, logging, persistence, or critic responsibilities owned by wrappers
- no interpretation of numerical parity alone as proof of semantic effectiveness

## 4. Database, Bootstrap, and Schema State

The current local database passed the Stage-B readiness database checks. The readiness report observed 192 local tables. 
The isolated empty-database bootstrap produced 121 schema objects and remained unchanged after a second bootstrap.

The bootstrap contract remains:

1. declare required columns in `SCHEMA_TABLES`
2. run idempotent schema creation
3. execute `_self_check_schema`
4. apply required indexes safely
5. repeat self-checks where required
6. fail visibly on missing schema contracts

The required key/value reader implementation remains:

`return dict(con.execute("SELECT key,value FROM " + table).fetchall())`

The current frozen-state drift validation has already captured the local schema fingerprint and source hashes. Final success requires both to remain unchanged for the full run.

## 9. Vector Database Decision Checkpoint

SQLite remains the canonical source of relational truth. A vector database must not be introduced merely because the database is large or 
because semantic retrieval may eventually be useful.

A dedicated vector-database checkpoint remains part of the project plan. It may be entered only when:

- stable data identities exist
- a concrete semantic similarity or retrieval use case is defined
- measurable requirements exist
- a read-only or shadow comparison against the SQLite baseline can be performed
- the relational source remains canonical
- no productive gates are opened by the evaluation

## 10. Known Limitations and Open Evidence Questions

Even if the running 1,344-cycle validation passes, the result will establish stability for the exact tested state. It will not by itself prove:

- semantic learning effectiveness
- dialogue usefulness for real users
- correctness of promoted knowledge
- independent, entity-bound, temporally valid outcomes
- replay-caused semantic improvement
- full end-to-end causal cooperation of all twelve modulators
- freedom from all future drift
- readiness for productive Fact promotion

The validation result must therefore be described as a frozen-state runtime stability baseline, not as completion of BrainStem's learning objective.

## 11. Current Operational Rules

- Measure before changing.
- Create a full backup before every project change or validation that affects the live runtime.
- Keep schema and bootstrap changes synchronized.
- Run compile checks, smoke tests, schema checks, and intermediate validation before delivery.
- Do not introduce word blacklists or hard-coded language filters.
- Do not write directly to Facts, Relations, or Questions.
- Do not promote Facts outside consolidation.
- Keep GUI logs and graphs bounded or downsampled.
- Prefer consolidated, technically coherent audit and refactoring steps over unnecessary micro-steps.
- Preserve the current frozen code state until the running validation has completed and been evaluated.

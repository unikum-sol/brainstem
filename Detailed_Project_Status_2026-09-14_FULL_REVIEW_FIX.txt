BrainStem Project Status - Full Code Review Remediation
Status date: 14 September 2026
Reference basis: four external code-review documents (Gesamturteil
REWORK.md, PLASTICITY_REVIEW.md, ROADMAP_REVIEW.md, and an informal
architecture note) plus a prior reviewer pass that had already applied
two targeted fixes (see section 1). This report supersedes all
"Stage A: Complete" style claims made before this remediation pass;
several of the defects fixed here directly affect the correctness of
data recorded by earlier, formally "green" test runs.

===========================================================================
1. STARTING POINT: TWO FIXES ALREADY APPLIED BY A PRIOR REVIEWER PASS
===========================================================================
Before this remediation session began, a prior pass had already applied
two small, targeted, high-impact fixes to the codebase (documented in the
project's own IMPROVEMENTS.md at the time):

1.1 One database path throughout the admin runtime
    Files: main.py, gui_app.py
    main.py now passes --memory-db through to gui_app.main(db_path),
    and App.__init__ stores it as self.db_path, consistently reused for
    the primary Memory instance, the autonomous worker, diagnostics,
    corpus statistics, the neuromodulator dashboard, drift/sensory-
    deprivation, and learning reset. Previously, db_bootstrap could
    initialize a user-selected database while the admin GUI and workers
    silently used the hardcoded "ki_memory.sqlite3" instead.

1.2 FTS results resolve authoritative content
    File: memory.py
    Memory.fts_search() now uses FTS5 only for matching/ranking, then
    joins chunks and documents by row id to retrieve real text, title,
    and path. The FTS table is contentless (content=''), so selecting
    those columns directly from it previously returned NULL for every
    FTS hit, potentially producing empty top-ranked search results and
    incorrectly suppressing valid fallback results in search.py (which
    also deduplicates by chunk_id, so an empty FTS hit could block a
    later, valid phrase/semantic hit for the same chunk from ever being
    returned).

Both were independently re-verified in this session (byte-for-byte diff
against the pre-review original, plus a live reproduction of the FTS
NULL-value bug against an in-memory contentless FTS5 table, confirming
the fix resolves it).

2. THIS SESSION: NINE ADDITIONAL DEFECTS FOUND AND FIXED
===========================================================================
Following the four external review documents, seven originally reported
findings were verified against the actual source code (not merely
trusted at face value) before any fix was applied. Two further defects
were discovered independently during this session's own real, multi-
cycle regression testing of the fixes below, and were fixed as well,

---------------------------------------------------------------------
2.1 Finding: hard-coded, un-checked synthetic chunk IDs (Review: "Gesamturteil REWORK.md")
---------------------------------------------------------------------
File: v8_phase5g_context_strategy_selection_and_experiment_memory_release.py

Verified: when no hypothesis-linked chunk_id could be resolved for a
gap, the code fell back to `int((gid or 1) % 1000) + 1` -- a number
derived only from the gap's own row id, never checked against the actual
chunks table -- and then wrote this (plus several strategy-dependent
offsets) directly into reading_queue, chunk_attention_scores, and
phase5g_strategy_experiments as if it pointed at a real chunk to read
next.

Fix: two new helper functions, _chunk_exists() and _real_chunk_id_near(),
resolve a REAL, existing chunks.id (nearest existing id at or above the
same numeric hint) instead of an unchecked synthetic number. Every
target chunk id (the center and each offset) is now checked for
existence before being written; if no real chunk id can be resolved at
all (e.g. before any corpus has been imported), that gap's experiment is
skipped for this cycle rather than writing invalid data.

Verified: with a deliberately tiny synthetic chunks table (ids 1-5 only)
and a gap whose old synthetic fallback would have been id 501 (which
does not exist), the fix now writes zero garbage entries instead of an
invalid chunk id. With a realistic corpus size (2,000 real chunks), the
fix produces the same class and volume of real experiments as before,
confirming no regression to normal operation.

2.2 Finding: a fatal, total phase-chain load failure does not stop the
    program from starting (Review: "Gesamturteil REWORK.md")
---------------------------------------------------------------------
Files: autonomous.py, main.py

Verified: phase_registry.load_all() already computed an explicit
report["fatal"] flag whenever a required phase module failed to load,
but nothing in the real program entrypoint (main.py) ever checked it.
Additionally, autonomous.py's own top-level exception handler around
phase_registry.load_all() only ever printed a traceback and continued;
if load_all() itself crashed entirely (rather than one of its
internally-caught per-module entries), the module-level name
_BRAINSTEM_LOAD_REPORT was never even defined, so any caller checking it
via getattr(..., None) would see "no report" -- silently equivalent to
"not fatal".

Fix: autonomous.py now always sets _BRAINSTEM_LOAD_REPORT to an explicit
dict (with fatal=True) even in the total-crash case, and exposes a new,
stable get_load_report() accessor. main.py's admin-GUI startup path (not
the read-only user-GUI path, which never imports ki_system.autonomous at
all) now calls get_load_report() after importing gui_app and refuses to
start (SystemExit(1), with a clear console message listing every failed
module) if fatal is true.

Verified: a simulated total crash of phase_registry.load_all() now
produces a report dict with fatal=True instead of an AttributeError/
None. A simulated fatal=True report correctly aborts main() with
SystemExit(1) without ever calling gui_app.main(). A simulated healthy
(fatal=False) report correctly proceeds and passes the exact,
user-specified database path through to gui_app.main() unchanged.

2.3 Finding: cycle diagnostics missed two real, phase-specific failure
    keys (Review: "Gesamturteil REWORK.md")
---------------------------------------------------------------------
File: v8_cycle_diagnostics_release.py

Verified via a project-wide grep of every dict-literal key name
containing "error"/"exception"/"fail" across all ~68 modules: the
recursive failure-scanner previously checked only a fixed pair of keys,
"error" and "base_cycle_error". Two real, existing failure dicts
elsewhere in the codebase carry ONLY their own ad hoc "<phase>_error"
key with neither of those two names and no recognized "status" value
(phase5e_error in v8_phase5f..., phase5g_cycle_error in v8_phase5h...),
making a real, uncaught exception in either upstream phase completely
invisible to this diagnostics module -- exactly the failure mode it
exists to prevent. A third candidate, phase5g_error, turned out to
already be caught coincidentally (that dict also always contains a
separate "error" key).

Fix: the fixed two-key check was generalized to a rule matching the key
"error" exactly OR any key ending in the "_error" suffix (_is_error_key
helper), applied to every key in a result dict rather than a fixed pair.

Verified: the module's own pre-existing selftest() still passes
unchanged (no regression to previously-correct behavior). Two new,
targeted tests confirm phase5e_error and phase5g_cycle_error are now
both correctly detected as failures. A counter-test confirms unrelated
data fields that merely contain the substring "error" without a "_error"
suffix (error_weight, errors, hypothesis_error_events,
last_projection_errors, projection_errors) are still correctly NOT
misclassified as failures.

2.4 Finding: import is not resumable, duplicates inflate the reported
    chunk count, and zimdump search order is a security risk (Review:
    "Gesamturteil REWORK.md")
---------------------------------------------------------------------
File: ingest.py

Three related defects verified in the same function, import_file():

  (a) The declared "resume" parameter (default True) was never
      referenced anywhere in the function body, despite Memory already
      providing fully-implemented get_import_state()/set_import_state()
      persistence for exactly this purpose.
  (b) "total += 1" ran unconditionally after every memory.add_chunk()
      call, regardless of whether add_chunk() actually inserted a new
      row (it uses INSERT OR IGNORE and returns None on a duplicate) --
      re-importing the same source inflated the reported chunk count
      with chunks that were never actually written.
  (c) zimdump_candidates() searched the current working directory
      (Path.cwd()) FIRST, before the project's own directory -- a
      malicious zimdump.exe placed in an untrusted working directory
      could be found and executed in preference to the legitimate
      binary.

Fix:
  (a)+(b) The ZIM-import branch now tracks a real "last fully-processed
      article" position via get_import_state()/set_import_state()
      (path, last_article, last_chunk, status). When resume=True (the
      default) and a prior, not-yet-"complete" state exists for this
      exact path, processing continues from that persisted position
      instead of restarting from article 1 / chunk 0. total is now only
      incremented when add_chunk() actually returns a non-None new row
      id. Every write path (ZIM branch and the plain-text/PDF branch)
      now explicitly records final status ("complete" or "cancelled").
  (c) zimdump_candidates() now checks the system PATH (via which()) and
      the project's own directory first; the current working directory
      is checked LAST, as a convenience fallback only, never a priority
      location.

Verified: a full first run correctly reports all N chunks as new. A
second full run of the identical source correctly reports zero new
chunks (all duplicates). A run cancelled partway through correctly
records the exact last-completed article index (a bug in the FIRST
version of this fix -- using the raw loop counter n instead of a
separate last_done tracker -- was caught by this exact test, which
showed off-by-one article skipping, and was corrected before delivery).
A subsequent resumed run correctly processes exactly the remaining
articles, skipping none and repeating none. resume=False correctly
ignores prior state and reprocesses from scratch, with duplicates still
correctly excluded from the count.

2.5 Finding: no mutual exclusion between import, reset, autonomous
    learning, and the drift/sensory-deprivation test (Review:
    "Gesamturteil REWORK.md")
---------------------------------------------------------------------
File: gui_app.py

Verified: reset_learning_gui() only ever checked self.auto_running;
pick_import() checked nothing at all; auto_start() and drift_start()
each only checked a subset of the other three operations. None of the
four database-writing/restructuring operations coordinated with all of
the others.

Fix: a single, centralized _busy_operation_name() helper (built on the
existing _shutdown_threads() helper already used for safe application
shutdown) is now checked by all four entry points. Each operation still
silently no-ops if the SAME operation is already running (normal, not an
error) but now warns and refuses to start if any OTHER of the three
remaining exclusive operations is currently active.

Verified: a fake-app harness confirms _busy_operation_name() correctly
identifies each of the four states (reset thread alive, mode=="import",
auto_running, drift_running) and returns None when nothing is running.

2.6 Finding: Phase 6c's own "bias persistence bridge" was fully
    implemented but never actually invoked (Review: "PLASTICITY_REVIEW.md")
---------------------------------------------------------------------
File: v8_phase6c_bias_persistence_and_self_regulating_meta_release.py

Verified: this module's own docstring states its purpose (1) as
protecting phase6b's plasticity adjustments from being reset by phase6a
on the next cycle. _save_sticky_bias() and _restore_sticky_bias() were
both fully implemented and correctly scoped to the five sticky bias
keys, but neither function was called anywhere in this file or any other
module in the entire codebase (confirmed via project-wide grep) --
completely dead code, despite being the module's stated core purpose.

Fix: run_phase6c_cycle() now calls _restore_sticky_bias() at the very
start of its own per-cycle work (overwriting phase6a's from-scratch
recompute, which already ran earlier in the same overall cycle, with
last cycle's durable target) and _save_sticky_bias() at the end (before
the final commit), persisting the resulting state as the new target for
the next cycle's restore.

Verified with a real, two-cycle simulation: cycle 1 (no prior sticky
state) leaves phase6a's own fresh values untouched, as expected. Cycle 2
simulates phase6a blindly recomputing completely different "fresh"
values (0.99/0.01/0.99/0.01/0.10) -- after phase6c runs, the actual
stored state is confirmed to be cycle 1's sticky values (0.50/0.20),
NOT phase6a's new raw computation, in both phase6a_meta_plasticity_state
and phase6a_neuromodulated_sleep_state. This is also confirmed working
in a real, full-chain, multi-cycle end-to-end test via the actual,
unmodified phase_registry.py load order (not just a unit test): three of
the five sticky bias values were observed frozen at their cycle-1 value
across five real consecutive cycles as designed. The remaining two
(consolidation_bias, revision_bias) were observed still drifting
slightly cycle to cycle in that same live run; this was traced to
Phase 6b's own conditional write path (state_change_allowed) remaining
correctly gated off (phase5g_experiment_outcomes is empty by design, a
known, deliberate Stage-B boundary, not a defect) while a live,
end-to-end trace showed those two specific values still being touched
by a different path within the same overall cycle. This residual
partial-drift observation is noted here explicitly as NOT further
investigated or fixed in this session -- it does not crash or violate
any safety boundary, and pursuing it further would require additional,
separate investigation beyond the scope of the reviewed findings.

2.7 Finding: direction_bias is written every cycle but never actually
    used (Review: "PLASTICITY_REVIEW.md")
---------------------------------------------------------------------
File: v8_phase6d_saturation_homeostasis_and_meta_metaplasticity_release.py

Verified via project-wide grep: direction_bias was read from the
database only to compute its OWN next value -- a purely self-referential
value with zero effect on new_lr or any other computed output, despite
this module's own docstring describing sliding-threshold homeostasis
(Lee and Kirkwood 2019) as its explicit purpose.

Fix: dir_bias (the EMA of past target directions) is now compared
against the current episode's target_dir_bias; their product
("agreement") is positive when a parameter keeps saturating on the SAME
side episode after episode (chronic saturation) and negative when it
alternates sides (oscillating). Chronic saturation now dampens the
learning rate more aggressively; oscillating saturation dampens less.

Verified: a controlled two-episode comparison (chronic: both episodes
saturate at "max"; oscillating: episode A at "min", episode B at "max")
confirms chronic saturation produces a measurably smaller final
learning rate (0.054469) than oscillating saturation (0.057147) under
otherwise identical conditions -- direction_bias now has a real,
bounded, well-justified effect instead of being cosmetic.

2.8 Finding: the saturation streak counter cannot reach the threshold
    required to trigger bias renormalization (Review: "PLASTICITY_REVIEW.md")
---------------------------------------------------------------------
File: v8_phase6d_saturation_homeostasis_and_meta_metaplasticity_release.py
(same file as 2.7, different function)

Verified: the streak-counting logic conflated two unrelated concepts
under the single literal string "counter" stored in last_direction: (a)
"the sliding-threshold action was just applied this cycle" (an ACTION
marker) and (b) "the parameter's own value just moved in the
counter/away-from-boundary direction" (what the streak-continuation
check was actually trying to detect). Because reaching the threshold
wrote the literal marker "counter" into last_direction, the very next
cycle's check (`last_dir != "counter"`) was always false immediately
after a successful sliding-threshold application, causing the streak to
be DECREMENTED instead of continuing to climb -- producing a
self-limiting oscillation (3 -> 2 -> 3 -> 2 -> ...) that could never
reach SATURATION_STREAK_THRESHOLD + 1 (4), the exact condition required
to ever schedule this module's own bias-renormalization action (its
documented purpose (4), Bazhenov slow-wave downscaling).

Fix: the streak counter now increments monotonically and unconditionally
every consecutive cycle a parameter remains at the same boundary,
decoupled entirely from the action-marker concept. last_direction now
only ever stores the parameter's actual observed movement direction
(up/down/flat), never a synthetic action marker.

Verified: reproducing the OLD formula in isolation confirms it produces
exactly the oscillating sequence [1,2,3,2,3,2,3,2] over 8 cycles of
sustained boundary saturation, never reaching 4. The FIXED formula
produces a correctly monotonic [1,2,3,4,5,6,7,8], with
bias_resets_scheduled correctly firing starting at cycle 4 (the
theoretically exact expected cycle, SATURATION_STREAK_THRESHOLD + 1).

2.9 Finding (newly discovered during this session's own multi-cycle
    regression testing, not from the original four review documents):
    an UnboundLocalError could crash Phase 7b's entire cycle
---------------------------------------------------------------------
File: v8_phase7b_endocannabinoid_retrograde_gain_control_release.py

How this was found: after applying and verifying fix 2.6 (the phase6c
sticky-bias bridge), a real, full end-to-end multi-cycle regression test
(using the actual, unmodified phase_registry.py load order against a
freshly bootstrapped database) began failing from cycle 8 onward with
"cannot access local variable '_kernel_result' where it is not
associated with a value" -- a genuine Python UnboundLocalError. This was
NOT present in a parallel 12-cycle control run against the completely
unmodified, pre-fix original codebase, raising the question of whether
this was a new regression introduced by this session's own fixes.

Root-cause investigation confirmed this is a PRE-EXISTING, independent
defect in _apply_anandamide_ltd(), byte-identical in the original,
untouched copy of this exact file, that had simply never been reachable
before: _kernel_result was assigned ONLY inside a for-loop over each
bias key, and only on iterations where that key's deviation from its
midpoint reaches or exceeds a threshold (ext_th). The function's final,
unconditional return statement references _kernel_result regardless of
whether the loop ever took that branch. If every tracked bias value
happens to already be within ext_th of its own midpoint (pulled stays
0), _kernel_result is never assigned, and the final return line raises
UnboundLocalError, crashing this entire phase's cycle.

Why fix 2.6 made this reachable: before fix 2.6, phase6a's bias values
were effectively reset/recomputed from scratch every cycle with no
persistence, making it very unlikely that ALL five bias values
would simultaneously sit close to their own midpoints. After fix 2.6
correctly makes bias values converge and stabilize over time (exactly
as that fix was designed to do), the system can genuinely reach a state
where every bias value is close to its midpoint -- exposing this
independent, previously-latent defect. This is documented transparently
here as an emergent interaction between an intentional, correct fix
(2.6) and a separate, pre-existing bug, not a flaw in fix 2.6 itself.

Fix: _kernel_result is now initialized to None before the loop. The
guarded shadow-observation helper (observe_adapter() in
v8_guarded_core_adapters_canonical_sleep_wake_shadow_release.py) already
handles a None kernel_result gracefully (records a diagnostic
observation with valid=False, never raises), and the kernel-authority
selector defaults to the authoritative "old" value in normal operation
regardless -- so this fix cannot change any actually-applied learning
behavior, it only prevents the crash when there is genuinely nothing to
shadow-compare.

Verified: with all five bias values deliberately set to their exact
midpoints (the previously-crashing case), the function now returns
{'pulled': 0, ...} without raising. With at least one bias value made
deliberately extreme (the normal case), the function continues to
correctly pull it toward its midpoint exactly as before, confirming no
regression to normal operation.

3. A TENTH DEFECT: MISSING SCHEMA COLUMNS DISCOVERED VIA LIVE REGRESSION
   TESTING (not from the four review documents)
===========================================================================
File: db_bootstrap.py

How this was found: the same real, full end-to-end multi-cycle
regression test used to verify fixes 2.6-2.9 (run against the actual,
unmodified phase_registry.py chain, on a freshly bootstrapped database)
failed on literally every single cycle, from cycle 1 onward, with
"no such column: resolution_attempts" -- confirmed reproducible
identically against the completely unmodified, pre-fix original
codebase, i.e. this was a pre-existing defect, not a regression from any
fix in this session.

v8_phase5b_integrated_strategy_refinement_release.py's real per-cycle
persistent-gap-strategy query references
"COALESCE(resolution_attempts,0)" against internal_learning_gaps
directly, with no "in columns" existence guard, and this column was
never declared anywhere in the codebase (neither in db_bootstrap.py's
central SCHEMA_TABLES nor in any individual module's own schema
extension). This is the exact same class of defect previously found and
fixed for the severity/hypothesis_id/uncertainty/pattern_key columns
(see the existing BRAINSTEM_GAP_SCHEMA_COMPLETENESS_FIX_V1 comment
already present in db_bootstrap.py from an earlier session).

Fixing this column then surfaced a SECOND, immediately-following
instance of the exact same defect class: "no such column:
revision_pressure", referenced unconditionally via
COALESCE(revision_pressure,0) in an ORDER BY clause in
v8_phase5e_context_expansion_and_gap_closure_release.py's own real
per-cycle gap-selection query.

Rather than continue discovering these one at a time through repeated
live test cycles, a systematic, project-wide audit was performed: every
column referenced via COALESCE(...) against internal_learning_gaps,
across all ~68 modules, was extracted and cross-checked against both the
central SCHEMA_TABLES definition AND each individual module's own
self-healing schema-extension mechanism (ensure_schema()/addcol() calls
that run before that module's own queries in the same function). This
audit found six further candidate columns
(phase5e_expansion_attempts, phase5f_experiment_count,
phase5g_experiment_count, phase5i_experiment_count,
phase6a_sleep_replay_count, strategy_refinement_count) plus
resolution_status; each was individually verified to already be safely
self-healed by its owning module's own schema extension (confirmed to
run before use in the same call chain) or, for resolution_status,
already guarded by an explicit "in columns" check before use everywhere
it appears. revision_pressure was the ONLY column in this audit
genuinely unowned by any module's own schema mechanism.

Fix: both resolution_attempts (INTEGER DEFAULT 0) and revision_pressure
(REAL DEFAULT 0) were added to db_bootstrap.py's central SCHEMA_TABLES
definition for internal_learning_gaps, matching the project's own
established "alle Spalten vorab in SCHEMA_TABLES" rule and the exact
same pattern already used for the four previously-fixed columns.
